# HML-LiDAR RevA — macOS workstation configuration

## English version

# Guide 4: Configuring the macOS post-processing workstation

This guide describes the macOS configuration used for the HML-LiDAR RevA
post-acquisition workflow.

The Mac workstation is used for:

1. transferring raw ROS 2 acquisitions from the Raspberry Pi;
2. running DLIO post-processing inside the RevA Docker environment;
3. optionally performing ZUPT-assisted retrospective reinitialization;
4. assembling multiple acquisition sessions with Pegar;
5. revising an existing multi-session network;
6. inspecting and annotating the resulting point cloud;
7. extracting a VisualTopo-compatible `.tro` topographic representation.

The principal RevA macOS scripts are located in:

```text
PROTO/scripts/Mac/
```

The seven-stage workflow is:

```text
0_mission_sync.sh
        ↓
1_traiter_bag.command
        ↓
2_update_bag_EditeurTemporel_ZUPT.py   [optional]
        ↓
3_LancerPegar.command / Pegar.py
        ↓
4_LancerEditeur.command / EditeurReseau.py
        ↓
5-VisualisateurTopographiqueWithDensity.py
        ↓
6_ExtracteurTopographique.py
```

`7-VisualisateurTRO.py` is an optional visualization tool for the resulting
`.tro` files. It is not an additional processing stage.

---

## 1. macOS requirements

The RevA post-processing environment requires:

- macOS;
- Docker Desktop;
- SSH;
- `rsync`;
- a terminal application;
- AppleScript/Automation permissions for the DLIO processing interface.

The RevA Docker image uses a Linux `amd64` environment.

On Apple Silicon Macs, including M1, M2, M3 and M4 systems, Docker Desktop
runs this environment through `linux/amd64` emulation.

---

## 2. Install Docker Desktop

Install and start Docker Desktop for macOS.

Verify that Docker is available from the terminal:

```bash
docker --version
```

and:

```bash
docker info
```

Docker Desktop must be running during DLIO post-processing.

The data-transfer script `0_mission_sync.sh` does **not** require Docker.
Docker is required starting from the DLIO processing stage.

---

## 3. Clone the HML-LiDAR repository

Clone the repository on the Mac if this has not already been done:

```bash
git clone https://github.com/sbassetto/hml-lidar-cave-mapping.git
```

Enter the repository:

```bash
cd hml-lidar-cave-mapping
```

For the RevA release, use the corresponding RevA branch or release.

The Mac scripts are located in:

```text
PROTO/scripts/Mac/
```

---

## 4. Create the expedition-data directories

The RevA field-processing workflow uses a host-side data directory separate
from the source-code repository.

The reference field installation uses:

```text
~/Desktop/Expedition_Data/
```

with the following structure:

```text
Expedition_Data/
├── raw/
└── results/
```

Create these directories with:

```bash
mkdir -p "$HOME/Desktop/Expedition_Data/raw"
mkdir -p "$HOME/Desktop/Expedition_Data/results"
```

### `raw/`

This directory receives the raw ROS 2 bags transferred from the Raspberry Pi.

Typical acquisitions have names such as:

```text
cave_bag_YYYY-MM-DD_HH-MM-SS
```

### `results/`

This directory receives processed ROS 2 bags and other persistent outputs
generated by the post-processing environment.

The scripts themselves remain in the Git repository. They do not need to be
copied into `Expedition_Data`.

---

## 5. Configure SSH access to the Raspberry Pi

The transfer script uses `rsync` over SSH to retrieve the raw acquisitions
from the Raspberry Pi.

The RevA field Raspberry Pi was named:

```text
chinook.local
```

and the field user was:

```text
samuel
```

### 5.1 Generate an SSH key

If no SSH key is already configured on the Mac:

```bash
ssh-keygen -t rsa -b 4096
```

The default location can normally be accepted.

### 5.2 Install the public key on Chinook

```bash
ssh-copy-id samuel@chinook.local
```

The Raspberry Pi password may be requested during this operation.

Test the connection:

```bash
ssh samuel@chinook.local
```

For another installation, replace the username and host name with the
corresponding values.

---

## 6. Configure `0_mission_sync.sh`

The RevA transfer script is:

```text
PROTO/scripts/Mac/0_mission_sync.sh
```

Its field configuration defines:

```bash
RP_USER="samuel"
RP_HOST="chinook.local"
RP_PATH="/home/samuel/Cave_explorer/data/cave_data/"
LOCAL_BASE="/Users/samuel/desktop/Expedition_Data"
```

These values correspond to the RevA field installation.

For another computer or Raspberry Pi, edit them before using the script.

The transfer script creates the local `raw/` and `results/` directories if
necessary.

Make the script executable:

```bash
cd PROTO/scripts/Mac
chmod +x 0_mission_sync.sh
```

---

## 7. Transfer field acquisitions

Connect the Raspberry Pi and Mac to a network allowing SSH communication.

Run:

```bash
./0_mission_sync.sh
```

The script uses:

```text
rsync
SSH
--remove-source-files
```

to transfer the contents of:

```text
/home/samuel/Cave_explorer/data/cave_data/
```

to:

```text
~/Desktop/Expedition_Data/raw/
```

After a successful transfer, the RevA field script removes the remaining
contents of the Raspberry Pi acquisition directory.

This behavior is intentional in the RevA field workflow and frees storage on
the Raspberry Pi for subsequent acquisitions.

The raw data stored on the Mac therefore become the retained copy before
post-processing.

## 8. Configure the RevA Docker processing environment

The Docker configuration is located in:

```text
PROTO/scripts/Mac/
```

and is defined by:

```text
Dockerfile
docker-compose.yml
```

The RevA Compose configuration creates the container:

```text
hml_lidar_reva
```

from the image:

```text
hml-lidar-reva:local
```

The container uses:

```text
platform: linux/amd64
```

and remains active using:

```text
sleep infinity
```

so that the RevA processing scripts can launch ROS 2 processes with
`docker exec`.

---

## 9. Configure the Docker data volumes

The Docker Compose configuration supports two host environment variables:

```text
HML_RAW_DIR
HML_RESULTS_DIR
```

For the reference Mac configuration, set them to:

```bash
export HML_RAW_DIR="$HOME/Desktop/Expedition_Data/raw"
export HML_RESULTS_DIR="$HOME/Desktop/Expedition_Data/results"
```

They are mounted inside the RevA container as:

```text
Host                                             Container
------------------------------------------------------------------
$HML_RAW_DIR                                     /root/data
$HML_RESULTS_DIR                                 /root/ros2_ws/results
PROTO/configuration/                             /root/hml/config
PROTO/scripts/Mac/                               /root/hml/scripts
```

The configuration and script directories are mounted read-only inside the
container.

### Optional `.env` configuration

To avoid exporting these variables for each terminal session, a local `.env`
file can be created in:

```text
PROTO/scripts/Mac/
```

with:

```text
HML_RAW_DIR=/Users/samuel/Desktop/Expedition_Data/raw
HML_RESULTS_DIR=/Users/samuel/Desktop/Expedition_Data/results
ROS_DOMAIN_ID=0
HML_ROSBRIDGE_PORT=9090
```

Adapt `/Users/samuel/` to the local account when necessary.

Do not use this example path unchanged on another computer.

The publication processing environment stores the compiled software stack
under:

```text
/opt/hml_ws
```

The ROS 2 setup file used by the processing scripts is:

```text
/opt/hml_ws/install/setup.bash
```

The active RevA DLIO parameter file is mounted as:

```text

```

The raw acquisitions are available under:

```text

```

```text
/root/ros2_ws/results/
```

The processing scripts detect this RevA layout automatically.

A compatibility path remains in `1_traiter_bag.command` for the historical
field-processing container, but the RevA publication environment is the
reference configuration.

## 12. Configure macOS Automation permissions

AppleScript automation is used by:

```text

```

to open and manage the ROS 2/DLIO terminal sessions.

It is **not** required by `0_mission_sync.sh`.

During the first execution of `1_traiter_bag.command`, macOS may request
permission for Terminal to control Terminal or System Events.

Allow the requested automation access.

If it was previously denied, open:

```text
System Settings
    → Privacy & Security
    → Automation
```

and enable the appropriate Terminal permissions.

## 14. Run DLIO post-processing

The principal DLIO processing command is:

```bash
./1_traiter_bag.command
```

If no bag is supplied as an argument, the script opens a macOS interface
allowing the operator to:

```text
Select one ROS 2 acquisition
```

or:

```text
Process the /raw directory
```

For each selected acquisition, the script orchestrates several ROS 2
processes inside `hml_lidar_reva`.

The processing sequence includes:

```text
T1 — DLIO odometry
T2 — ROS 2 bag playback
T3 — rosbridge
T5 — recording of the processed ROS 2 topics
```

The raw bag is replayed with simulated ROS time.

The operator waits until the T2 playback has finished and then presses Enter
in the main processing terminal.

The script then:

1. sends an interrupt to the ROS 2 bag recorder;
2. allows the output database and metadata to finalize;
3. terminates residual ROS processes;
4. closes the processing terminal windows.

Processed bags use the suffix:

```text
_result
```

and are written to:

```text
~/Desktop/Expedition_Data/results/
```

through the Docker volume mapping.

---

## 15. Processing a different data location

`1_traiter_bag.command` accepts host-side environment variables.

The main data root can be changed with:

```bash
HML_DATA_ROOT="/path/to/Expedition_Data" ./1_traiter_bag.command
```

The raw directory can be explicitly overridden with:

```bash
HML_RAW_DIR="/path/to/raw" ./1_traiter_bag.command
```

The container name can also be overridden if necessary:

```bash
HML_CONTAINER_NAME="container_name" ./1_traiter_bag.command
```

The RevA reference container remains:

```text
hml_lidar_reva
```

---

## 16. Optional ZUPT-assisted retrospective reinitialization

When required, the processed acquisition can be inspected with:

```text
2_update_bag_EditeurTemporel_ZUPT.py
```

This tool supports operator-guided retrospective reinitialization around a
selected stationary interval.

This stage is optional and should only be applied when justified by the
trajectory or processing result.

Detailed behavior is documented in:

```text
../../documentation/ZUPT_REINITIALIZATION_RevA.md
```

---

## 17. Multi-session registration with Pegar

After individual acquisitions have been processed, overlapping sessions can be
assembled using:

```text
3_LancerPegar.command
Pegar.py
serveur_alignement.py
```

Pegar provides operator-guided rigid registration between overlapping cave
segments.

The resulting transformations are stored explicitly so that the assembled
network remains traceable and revisable.

---

## 18. Revising an assembled network

An existing Pegar registration network can be reopened using:

```text
4_LancerEditeur.command
EditeurReseau.py
serveur_edition.py
```

A selected junction can be modified and the resulting transformation changes
propagated through the downstream network.

---

## 19. Point-cloud inspection and annotation

The RevA inspection and annotation tool is:

```text
5-VisualisateurTopographiqueWithDensity.py
```

It supports inspection of the reconstructed point cloud and the extraction of
operator-selected topographic information.

---

## 20. Topographic extraction

The RevA topographic extractor is:

```text
6_ExtracteurTopographique.py
```

It generates a VisualTopo-compatible:

```text
.tro
```

representation from the processed and annotated LiDAR data.

The former `lidar_to_vtopo.py` name is not part of the RevA workflow.

---

## 21. Optional `.tro` visualization

The utility:

```text
7-VisualisateurTRO.py
```

can be used to inspect the resulting `.tro` file.

It is an optional visualization utility and is not an eighth processing stage.

---

## 22. Rosbridge and optional visualization

The RevA Docker configuration exposes:

```text
9090:9090
```

for rosbridge-compatible visualization.

The port can be changed before the container is created by setting:

```bash
export HML_ROSBRIDGE_PORT=9091
```

or through the local `.env` file.

Only one local container or process can bind a given host port at a time.

# Version française

# Guide 4 : Configuration du poste macOS pour le post-traitement

Ce guide décrit la configuration macOS utilisée pour la chaîne de
post-traitement HML-LiDAR RevA.

Le poste Mac est utilisé pour :

1. transférer les acquisitions ROS 2 brutes depuis le Raspberry Pi ;
2. effectuer le traitement DLIO dans l'environnement Docker RevA ;
3. effectuer, si nécessaire, une réinitialisation rétrospective assistée par
   ZUPT ;
4. assembler plusieurs sessions d'acquisition avec Pegar ;
5. réviser un réseau multi-session existant ;
6. inspecter et annoter le nuage de points obtenu ;
7. extraire une représentation topographique compatible VisualTopo au format
   `.tro`.

Les principaux scripts macOS RevA se trouvent dans :

```text
PROTO/scripts/Mac/
```

La chaîne de traitement en sept étapes est :

```text
0_mission_sync.sh
        ↓
1_traiter_bag.command
        ↓
2_update_bag_EditeurTemporel_ZUPT.py   [optionnel]
        ↓
3_LancerPegar.command / Pegar.py
        ↓
4_LancerEditeur.command / EditeurReseau.py
        ↓
5-VisualisateurTopographiqueWithDensity.py
        ↓
6_ExtracteurTopographique.py
```

`7-VisualisateurTRO.py` est un outil optionnel de visualisation des fichiers
`.tro`. Il ne constitue pas une étape supplémentaire du traitement.

---

## 1. Prérequis macOS

L'environnement de post-traitement RevA nécessite :

- macOS ;
- Docker Desktop ;
- SSH ;
- `rsync` ;
- une application Terminal ;
- les autorisations d'automatisation AppleScript nécessaires à l'interface de
  traitement DLIO.

L'image Docker RevA utilise un environnement Linux :

```text
amd64
```

Sur les Mac Apple Silicon, notamment M1, M2, M3 et M4, Docker Desktop exécute
cet environnement par émulation `linux/amd64`.


Lorsqu'aucun bag n'est fourni en argument, une interface macOS permet de :

```text
sélectionner une acquisition ROS 2
```

ou :

```text
traiter le contenu du dossier /raw
```

Pour chaque acquisition, le script orchestre plusieurs processus ROS 2 dans
`hml_lidar_reva` :

```text
T1 — odométrie DLIO
T2 — lecture du bag ROS 2
T3 — rosbridge
T5 — enregistrement des topics traités
```

Le bag brut est relu en temps ROS simulé.

Lorsque la lecture T2 est terminée, l'opérateur appuie sur Entrée dans le
terminal principal.

Le script :

1. interrompt proprement l'enregistrement ROS 2 ;
2. laisse le temps à la base de données et aux métadonnées de se finaliser ;
3. arrête les processus ROS résiduels ;
4. ferme les fenêtres Terminal utilisées pour le traitement.

Les acquisitions traitées prennent le suffixe :

```text
_result
```

et sont stockées sous :

```text
~/Desktop/Expedition_Data/results/
```

par l'intermédiaire du volume Docker.

## 15. Utiliser un autre emplacement de données

`1_traiter_bag.command` accepte plusieurs variables d'environnement.

Pour définir une autre racine de données :

```bash
HML_DATA_ROOT="/chemin/vers/Expedition_Data" ./1_traiter_bag.command
```

Pour imposer un dossier `raw` particulier :

```bash
HML_RAW_DIR="/chemin/vers/raw" ./1_traiter_bag.command
```

Le nom du conteneur peut également être remplacé :

```bash
HML_CONTAINER_NAME="nom_du_conteneur" ./1_traiter_bag.command
```

Le conteneur de référence RevA reste :

```text
hml_lidar_reva
```

## 17. Assemblage multi-session avec Pegar

Après le traitement individuel des acquisitions, les sessions présentant un
recouvrement peuvent être assemblées avec :

```text
3_LancerPegar.command
Pegar.py
serveur_alignement.py
```

Pegar permet l'enregistrement rigide guidé par l'opérateur de segments de
grotte présentant un recouvrement naturel.

Les transformations obtenues sont conservées explicitement afin que
l'assemblage demeure traçable et révisable.

```text
serveur_edition.py
```

Une jonction peut alors être modifiée et les transformations correspondantes
propagées dans le réseau en aval.

## 22. Rosbridge et visualisation optionnelle

La configuration Docker RevA expose le port :

```text
9090:9090
```

pour les visualisations compatibles rosbridge.

Le port peut être modifié avant la création du conteneur, par exemple :

```bash
export HML_ROSBRIDGE_PORT=9091
```

ou au moyen du fichier `.env`.

Un même port hôte ne peut être utilisé simultanément que par un seul conteneur
ou processus local.
