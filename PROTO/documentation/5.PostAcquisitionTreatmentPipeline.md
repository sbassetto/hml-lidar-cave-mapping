# HML-LiDAR RevA — Post-acquisition processing pipeline

This document describes the post-acquisition workflow used in the RevA
field-tested HML-LiDAR prototype.

The workflow is intentionally modular. Raw underground acquisitions are first
transferred from the Raspberry Pi, then processed with DLIO. When necessary,
an acquisition can be restarted a posteriori using the ZUPT-assisted tool.
Independently processed sessions can subsequently be assembled with Pegar,
revised with the network editor, inspected for spatial-density anomalies,
and exported to a VisualTopo-compatible `.tro` representation.

The main RevA processing tools are located in:

`PROTO/scripts/Mac/`

---

## 1. Processing environment

The RevA workflow uses two complementary environments.

DLIO processing is performed inside the HML-LiDAR Docker/ROS 2 environment.
The corresponding RevA environment is defined by the repository Docker
configuration and preserves the field-tested ROS 2 Humble and DLIO software
stack.

Interactive post-processing tools such as Pegar, the network editor, the
ZUPT-assisted editor, the density viewer, and the topographic tools run from
the macOS host environment.

Python dependencies required by the host-side tools are defined in the
repository environment files.

---

## 2. Transfer of raw acquisitions

### Program

`0_mission_sync.sh`

The transfer script retrieves the ROS 2 acquisitions recorded by the
Raspberry Pi and transfers them to the post-processing workstation.

The script uses `rsync` for the transfer. After a successful transfer, the
source acquisition files are removed from the Raspberry Pi in order to free
storage space for subsequent underground recordings.

The transferred recordings constitute the raw input of the post-acquisition
workflow.

---

## 3. Primary DLIO processing

### Program

`1_traiter_bag.command`

The DLIO processing script launches the field-tested Docker/ROS 2 processing
environment and processes a selected ROS 2 acquisition.

The script starts the DLIO odometry node, replays the selected ROS 2 bag using
simulated ROS time, and records the resulting ROS 2 topics into a new processed
bag.

The active DLIO configuration is read from the `params.yaml` used by the DLIO
node inside the processing environment.

Field-tested parameter profiles are provided separately in:

`PROTO/configuration/dlio_profiles/`

These profiles correspond to different acquisition geometries encountered
during RevA testing. They document empirical configurations used during
a-posteriori processing and are not presented as globally optimal DLIO
parameters.

The resulting processed bags provide, among other topics, the trajectory
(`/path`) and keyframe point cloud (`/kf_cloud`) required by the subsequent
RevA tools.

---

## 4. Optional ZUPT-assisted restart

### Program

`2_update_bag_EditeurTemporel_ZUPT.py`

This step is optional and is used when an acquisition contains an odometric
divergence or when a later portion of the recording must be reprocessed from a
new initialization point.

The operator simultaneously selects:

- a processed bag used for visual inspection;
- the corresponding raw acquisition.

The application displays the processed geometry as a function of time and
allows the operator to select a restart point.

The program then creates a new raw ROS 2 bag beginning at the selected
location. Before the retained raw data, it inserts a synthetic stationary
initialization interval of 5 seconds.

For this interval:

- angular velocity is set to zero;
- linear acceleration is estimated from up to 200 IMU samples preceding the
  selected cut;
- synthetic IMU samples are generated at 200 Hz;
- LiDAR data are repeated during the stationary initialization interval.

The generated bag can then be processed again with DLIO, potentially using a
different field-tested parameter profile.

This procedure is a retrospective ZUPT-assisted reinitialization mechanism.
It is distinct from an online zero-velocity update incorporated directly into
the DLIO estimator.

---

## 5. Multi-session registration with Pegar

### Programs

`3_LancerPegar.command`  
`Pegar.py`  
`serveur_alignement.py`

Pegar is used to connect independently acquired and independently processed
cave sessions.

The operator selects a sequence of processed ROS 2 bags containing overlapping
natural cave geometry. The alignment interface allows the operator to estimate
a rigid six-degree-of-freedom transformation between successive sessions.

Each accepted relative transformation is stored explicitly as a homogeneous
rigid transformation matrix and as a human-readable six-degree-of-freedom
parameter file.

The transformations are accumulated sequentially to construct a common
reference frame for the complete network.

Pegar produces:

- transformed intermediate point-cloud fragments;
- stored relative and absolute transformation matrices;
- a connected point cloud in PCD format;
- a connected ROS 2 bag containing transformed `/kf_cloud` and `/path`
  information.

The purpose of Pegar is not to replace automatic registration algorithms, but
to provide an operator-guided, target-free, persistent and inspectable
registration mechanism for difficult multi-session cave datasets.

---

## 6. Revision of an existing Pegar network

### Programs

`4_LancerEditeur.command`  
`EditeurReseau.py`  
`serveur_edition.py`

The network editor allows an existing Pegar junction to be reopened and
modified without rebuilding the entire network from the beginning.

The editor reconstructs the sequence of relative transformations stored by
Pegar, allows one of these transformations to be revised interactively, and
then recomputes the downstream absolute poses.

A revised network is exported as a new version rather than silently replacing
the previous result.

The revised version contains:

- the updated transformation matrices;
- a regenerated connected point cloud;
- a regenerated connected ROS 2 bag.

This mechanism makes the multi-session registration process revisable and
preserves the successive states of the reconstructed cave network.

## 7. Point-cloud inspection and density annotation

### Program

`5-VisualisateurTopographiqueWithDensity.py`

The density viewer is used to inspect a processed or connected point cloud and
identify spatial regions requiring operator attention.

The program voxelizes the point cloud and evaluates the local number of points
inside the resulting spatial cells. The operator can interactively adjust the
density-analysis parameters and inspect low-density or high-density regions.

Selected regions can be associated with textual technical observations.

Annotations are stored separately from the original LiDAR measurements in:

`annotations_densite.json`

The annotation file also preserves the density-analysis parameters used during
inspection.

The tool therefore adds an interpretive layer without modifying the underlying
LiDAR point coordinates.

---

## 8. Topographic extraction

### Program

`6_ExtracteurTopographique.py`

The topographic extractor converts a connected ROS 2 bag into a
VisualTopo-compatible `.tro` file.

The program uses:

- `/path` to derive the trajectory;
- `/kf_cloud` to recover the surrounding cave geometry.

The trajectory is spatially resampled to generate topographic stations.
For each station, a local slice of the point cloud perpendicular to the
trajectory is analysed.

RevA uses the following default extraction parameters:

- station spacing: 1.5 m;
- local slice thickness: 1.0 m;
- maximum local search radius: 70 m;
- number of radial splay sectors: 10.

The local point-cloud geometry is used to estimate left, right, up and down
distances and to generate additional radial splay observations.

The result is written as a VisualTopo `.tro` file.

This export provides interoperability between the dense HML-LiDAR
reconstruction and conventional cave-topography software. It should not be
interpreted as an independently controlled conventional survey.

---

## 9. Optional `.tro` visualization

### Program

`7-VisualisateurTRO.py`

This utility is not a separate processing stage of the seven-stage HML-LiDAR
workflow. It is an inspection and visualization tool associated with the
topographic export.

It reads a generated `.tro` file, reconstructs its stations, survey legs and
splay observations, and displays the resulting geometry in three dimensions.

When a corresponding PCD file is available, the tool can also display
geometric information derived from the dense point cloud.

The viewer can generate plan, profile and isometric representations and export
a PDF topographic report.

---

## 10. RevA processing sequence

The complete post-acquisition sequence is therefore:

```text
ROS 2 underground acquisition
        ↓
0_mission_sync.sh
        ↓
raw ROS 2 bags
        ↓
1_traiter_bag.command
        ↓
DLIO processed bags
        ↓
[optional]
2_update_bag_EditeurTemporel_ZUPT.py
        ↓
DLIO reprocessing
        ↓
3_LancerPegar.command / Pegar.py
        ↓
connected multi-session network
        ↓
[optional]
4_LancerEditeur.command / EditeurReseau.py
        ↓
revised network version
        ↓
5-VisualisateurTopographiqueWithDensity.py
        ↓
inspection and annotations
        ↓
6_ExtracteurTopographique.py
        ↓
VisualTopo-compatible .tro
        ↓
[optional]
7-VisualisateurTRO.py
```

The RevA workflow preserves raw acquisition, processed ROS 2 data,
registration transformations, network revisions, point-cloud annotations and
topographic exports as distinct artifacts. This separation supports inspection
and retrospective revision of the processing chain.
